# План проєкту: інформаційна система туристичної агенції

## 1. Тема та проблема предметної області

Система автоматизує онлайн-взаємодію клієнта з туристичною агенцією: пошук пропозицій, перегляд програми туру, бронювання місць, керування власними заявками, формування відгуків та оплату.

Без такої системи актуальність місць, контактні дані, підтвердження бронювання та інформація про оплату часто обробляються вручну. Це збільшує час відповіді, створює ризик подвійного резервування й ускладнює контроль стану заявки.

### Запропоноване рішення

Вебзастосунок складається з React SPA, Django REST API та постійної бази даних. Клієнт бачить актуальний каталог і виконує дії у власному кабінеті, а сервер централізовано застосовує правила доступності, власності, скасування й оплати.

Ключові результати:

* єдине джерело істини для турів, місць, бронювань і платежів;
* JWT-автентифікація та розмежування visitor/customer/admin;
* атомарне резервування доступних місць;
* перевірена інтеграція LiqPay без довіри до непідписаного browser status;
* відтворюване Docker Compose середовище.

## 3. Сутності предметної області

### 3.1. Користувач (`CustomUser`)

Розширює Django user model. Email є унікальним і використовується під час входу.

| Поле | Призначення |
| --- | --- |
| `id` | Первинний ключ |
| `username` | Ім'я користувача |
| `email` | Унікальна адреса та login identifier |
| `is_staff` | Ознака адміністративного доступу |

### 3.2. Тур (`TourDescription`)

Зберігає основну пропозицію: напрямок, дати, транспорт, харчування, ціни, акційні ознаки та доступні місця. Середній рейтинг і кількість відгуків обчислюються queryset-анотаціями.

Пов'язані сутності:

* `TourDetail` — програма, послуги й тематичні ознаки;
* `TourPhoto` — media-файли;
* `TourFeedback` — рейтинг 1–5 та коментар клієнта.

### 3.3. Бронювання (`Booking`)

| Поле | Правило |
| --- | --- |
| `user`, `tour` | Установлюють власника та обрану пропозицію |
| `travel_start_date`, `travel_end_date` | Повинні входити у період туру |
| `adults`, `children` | Сума не перевищує `available_seats` |
| `contact_*` | Перевірені контактні дані |
| `total_price` | Розраховується сервером з актуальної ціни туру |
| `status` | `pending`, `confirmed` або `canceled` |
| `created_at` | Серверний timestamp |

Для пари user/tour дозволено лише одне активне бронювання. Скасоване бронювання не блокує створення нового.

### 3.4. Платіж (`BookingPayment`)

Має one-to-one зв'язок із бронюванням і зберігає суму, `is_paid`, merchant order ID, LiqPay payment ID та нормалізований статус.

Успішна операція переводить:

```text
BookingPayment.is_paid → true
BookingPayment.liqpay_status → success
Booking.status → confirmed
```

### 3.5. Обране та відгуки

* `LikedTour` унікально пов'язує користувача й тур.
* `TourFeedback` дозволяє одному користувачу залишити один відгук на тур.
* `AgencyReview` зберігає відгук про агенцію.
* `Reply` є відповіддю адміністратора на `AgencyReview`.

## 5. Користувацькі сценарії

### 5.1. Пошук туру

1. Відвідувач відкриває каталог.
2. Застосовує напрямок, дати, ціну, транспорт, харчування або тематичні фільтри.
3. Параметри синхронізуються з URL.
4. Selector формує відсортований і пагінований результат.
5. Користувач переходить на `/tour/:id`.

### 5.2. Створення бронювання

1. Клієнт входить або реєструється.
2. Відкриває форму конкретного туру.
3. Frontend перевіряє контактні поля й кількість місць.
4. Backend повторно перевіряє дати, місця та власника.
5. У транзакції зменшується `available_seats` і створюється `pending` booking.

### 5.3. Скасування

1. Клієнт відкриває власні бронювання.
2. UI показує можливість скасування лише до 14-денної межі.
3. Backend повторно застосовує правило незалежно від UI.
4. Статус змінюється на `canceled`, а місця повертаються один раз.

### 5.4. Оплата

1. Backend створює signed checkout payload для `booking-<id>`.
2. LiqPay widget виконує оплату.
3. Для публічного deployment LiqPay надсилає signed `server_url` callback.
4. Для localhost frontend викликає authenticated confirmation endpoint.
5. Backend перевіряє checkout signature та незалежно запитує LiqPay status API.
6. Payment і booking оновлюються в одній транзакції.
7. Frontend повторно завантажує список бронювань.

## 6. Маршрути та системні межі

Клієнтські маршрути, REST endpoints, request/response приклади та status codes підтримуються в кореневому [`README.md`](../README.md#rest-api-contract).

Основні API-групи:

| Prefix | Відповідальність |
| --- | --- |
| `/api/` | Реєстрація, JWT і поточний користувач |
| `/tours/` | Каталог, деталі, фото й відгуки |
| `/cabinet/` | Обране, бронювання та платежі |
| `/admin/` | Django administration |

Frontend і backend з'єднані HTTP/JSON-контрактом. Компоненти не звертаються до Django models напряму, а backend не залежить від структури React-компонентів.

## 7. Бізнес-правила та інваріанти

1. Клієнт не може призначити owner або booking status через request payload.
2. Дата завершення не може передувати даті початку.
3. Дати бронювання не виходять за межі дат туру.
4. Кількість гостей не перевищує доступні місця.
5. Повторне збереження існуючого booking не резервує місця вдруге.
6. Повторне скасування не повертає місця повторно.
7. Рейтинг має діапазон 1–5.
8. Змінювати review може лише його власник; reply створює лише admin.
9. Оплата не підтверджується лише за browser status.
10. Callback signature, `order_id` і сума мають збігатися з payment record.

## 9. Критерії приймання

Проєкт вважається готовим до демонстрації, якщо:

* `python manage.py test` завершується без помилок;
* `npm run test:run`, `npm run lint` і `npm run build` успішні;
* `docker compose config --quiet` валідний;
* після `docker compose up --build` три сервіси працюють, а `db` має стан healthy;
* користувач може пройти шлях register → login → booking → sandbox payment → confirmed status;
* інший користувач не може читати чи змінювати чужі booking/payment records;
* restart контейнерів без `--volumes` не видаляє PostgreSQL і media.

Актуальні результати тестування та команди запуску наведено в [`README.md`](../README.md#тестування).
